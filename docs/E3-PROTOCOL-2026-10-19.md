## So entsteht das echte E3-Protokoll (Server, Kaan)

Voraussetzungen auf dem Host: Kernel mit Landlock ABI ≥ 4 (Linux ≥ 6.7), `libpq5`,
Python ≥ 3.11, `git`, lokaler PostgreSQL-Testcluster mit `GENIUSNEW_TEST_ADMIN_DSN`
gemäß `docs/POSTGRES-B1.md`.

```sh
# Die eine Datei genügt — sie hat keine Repo-Imports (nur Standardbibliothek):
scp scripts/e3_fresh_clone.py server:~/e3_fresh_clone.py

# Auf dem Server:
export GENIUSNEW_TEST_ADMIN_DSN='host=127.0.0.1 port=5432 dbname=geniusnew_test_admin user=postgres'   # Beispiel, echte DSN nicht ins Repo
python3 ~/e3_fresh_clone.py \
    --repo https://github.com/Kaancodm/GeniusNew.git \
    --ref main \
    --dir ~/e3/GeniusNew \
    --protocol ~/e3/PROTOCOL.md
echo "Exit: $?"   # 0 = PASS, 1 = FAIL, 3 = BLOCKED (Grund steht im Protokoll)
```

Erfolgssignal: `E3 fresh-clone verdict: PASS (commit <SHA>)`, Exit 0 — volle Suite und
Demo (`PASS — … 15/15 attacks refused`) liefen auf diesem Host an diesem Commit.
Danach fehlt für Gate E3 noch die Betreiberstufe: Dienst nach C5-Anleitung bis
`python -I -m geniusnew serve` hochfahren (eigene OS-Nutzer, DB-Rollen,
Anker-Dienst), einen Job per `curl` über den Reverse-Proxy schicken, Dienst
kontrolliert stoppen — und `PROTOCOL.md` plus diese Schritte als E3-Protokoll mit
dem aufgelösten HEAD-SHA im PR ablegen. Erst dann darf in der Roadmap aus
„E3 offen" ein „erledigt" werden.

**Sicherheitshinweis:** Der Runner führt Code aus dem geklonten Repository aus
(Tests/Demo) — das ist der Sinn eines Fresh-Clone-Nachweises. Deshalb nur gegen das
eigene, vertrauenswürdige Repo und einen geprüften Ref laufen lassen.
